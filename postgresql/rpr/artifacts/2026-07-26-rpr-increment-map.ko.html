PF1은 흡수 차단 문제가 아니라 읽기 포인터 문제입니다

FIRST가 있으면 문맥 흡수가 막히는 것은 결함이 아니라 당연한 원칙입니다. 흡수는 “앞으로의 거동이 매치 시작 위치와 무관하다”를 전제하는데 FIRST는 정의상 match_start를 되돌아보므로 전제가 깨집니다. navFirstOffset이 잡힌 컨텍스트는 흡수 후보에서 빠지는 게 맞습니다.

PF1이 다투는 것은 그 아래 층입니다. 흡수가 되든 안 되든 tuplestore 읽기 포인터 하나를 두 위치가 번갈아 씁니다.

  -> spill 상태에서 행마다 (pos - matchStart) 튜플을 2회 훑음
  -> 매치당 Theta(길이^2) 물리 재읽기

측정이 두 설명을 갈라줍니다. PREV도 흡수를 막지만 spill에서 1.7 ms인 반면 FIRST는 5358 ms입니다(n=4000). 흡수 차단이 원인이면 둘이 비슷해야 합니다. 차이를 만드는 것은 읽기 포인터가 오가느냐뿐이고, EXPLAIN (ANALYZE, BUFFERS)의 temp read=2,154,477(n=2000)이 그 물리 재읽기를 그대로 보여줍니다. 결과값은 정확합니다(md5 동일).

수정안도 흡수를 건드리지 않습니다. 읽기 포인터를 둘로 쪼개 frontier 전용(행마다 +1)과 nav 전용(matchStart 근처 고정)으로 나누면 각각 상환 O(1)이 됩니다. markptr 하한(matchStartRow + navFirstOffset)은 그대로라 보존 구간도 흡수 판정도 변하지 않습니다. 정확성과 무관하므로 이번 범위 밖이고, 커밋 이후 항목으로 기록해 둡니다.

부록 — BASE / HEAD 실측

위 판정들을 두 벌을 실제로 빌드해 확인했습니다. BASE는 RPR-henson(3XXX 대역의 마지막 커밋), HEAD는 브랜치 팁입니다. 항목마다 새 DB에서 양쪽에 돌렸고, 아래에 재현 쿼리와 수정 전/후 출력 차이를 그대로 싣습니다. 쿼리는 각자 테이블을 만드므로 붙여넣으면 실행됩니다.

각 케이스에는 결함 유무와 무관하게 답이 정해지는 대조군이 붙어 있습니다 — 대조군이 없으면 그 테스트는 아무것도 증명하지 못합니다. X1은 assertion 결함이라 assert를 켜야 발화합니다.

-- Z4 / opt-window F6: run-condition blanket block on RPR windows
CREATE TEMP TABLE z_Z4_t (ts int, price int);
INSERT INTO z_Z4_t SELECT g, (g * 37) % 11 FROM generate_series(1, 30) g;

-- (1) Symptom: RPR window -> no "Run Condition:" line, filter degraded to
--     a Filter above the WindowAgg (full-partition NFA matching forced).
EXPLAIN (COSTS OFF)
SELECT * FROM (
  SELECT ts, row_number() OVER w AS rn FROM z_Z4_t
  WINDOW w AS (ORDER BY ts ROWS BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING
               AFTER MATCH SKIP TO NEXT ROW INITIAL
               PATTERN (a+) DEFINE a AS price > PREV(price))) s
WHERE rn <= 10;

-- (2) Non-RPR baseline: "Run Condition: (row_number() OVER w <= 10)" present.
EXPLAIN (COSTS OFF)
SELECT * FROM (
  SELECT ts, row_number() OVER w AS rn FROM z_Z4_t
  WINDOW w AS (ORDER BY ts ROWS BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING)) s
WHERE rn <= 10;

-- (3) Why blanket unblock is unsafe: count(*) claims MONOTONICFUNC_DECREASING
--     from frameOptions alone (int8.c), but over RPR reduced frames cnt is
--     match-dependent and non-monotonic (drops to 0 on unmatched rows, rises
--     again on later matches).  Under an unblocked build this query would get
--     a run condition and silently lose all matches after the first unmatched
--     row; on the current tree it returns every cnt>0 row (correct).
SELECT * FROM (
  SELECT ts, price, count(*) OVER w AS cnt FROM z_Z4_t
  WINDOW w AS (ORDER BY ts ROWS BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING
               PATTERN (b+) DEFINE b AS price > PREV(price))) s
WHERE cnt > 0 ORDER BY ts;
